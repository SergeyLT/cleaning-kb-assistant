# Production: GitHub Actions → GHCR → Coolify

Это универсальный маршрут для одного VPS. Linux/Windows до localhost описаны в [README](../README.md#быстрый-старт). Здесь предполагаются уже работающие Docker, Coolify и его HTTPS-прокси, доступ к GitHub/GHCR, собственный домен и ключ ProxyAPI. Loki, Alloy и Grafana нужны для централизованного мониторинга; приложение работает и без них. Установка этих систем в руководство не входит.

## Состав

[compose.production.yml](../compose.production.yml) запускает готовый образ приложения и Qdrant. SQLite и кеш эмбеддингов находятся в `app-data`, индекс — в `qdrant-data`. Реальные имена томов дополняются именем ресурса/Compose-проекта. Не переименовывайте ресурс или volumes без переноса данных.

Только `api` получает публичный домен; он слушает внутренний порт 8000. Ни `api`, ни Qdrant не имеют `ports:`. Приложение запускается пользователем 10001, один worker и одна реплика. Несколько экземпляров на одной SQLite не поддерживаются; блокировка предотвращает второй процесс. Миграции выполняются при старте с проверкой checksum. Compose заменяет контейнер, поэтому кратковременная недоступность при обновлении допустима; zero downtime не обещается.

`APP_VERSION` встроен в образ из полного commit SHA и возвращается в `/health` и логах. Не переопределяйте его в Coolify: иначе можно скрыть реально запущенную версию.

## 1. Подготовить GitHub и первый образ

Опубликуйте репозиторий самостоятельно, включите Actions, выберите `main` основной веткой. [Workflow](../.github/workflows/ci.yml) использует Ubuntu 24.04, Python 3.12, Node 24 и закреплённые commit SHA actions.

- PR: Python-проверки, pytest, шесть UI-сценариев и Docker build без публикации/deploy. Ключ модели не нужен.
- Push в main: те же Python/UI-проверки, затем одна сборка и публикация `latest` и `sha-<полный SHA>` в `ghcr.io/<owner>/<repository>` (нижний регистр).
- Ручной `workflow_dispatch`: только проверки/проверочная сборка, без публикации и deploy.
- Production deploy выключен, пока Repository Variable `PRODUCTION_DEPLOY_ENABLED` не равна строке `true`.

Право `packages: write` получает только job публикации после проверок; для GHCR используется встроенный `GITHUB_TOKEN`. На fork-PR нет production secrets. Доступ к исходникам checkout не сохраняет. Включите обязательный CI и защиту main в настройках репозитория по своей политике.

Первый push создаёт образ даже при выключенном deploy. После успешного workflow проверьте страницу Packages. Для публичного образа сделайте package публичным отдельно от репозитория; изменение видимости GitHub repo само по себе этого не гарантирует. Для приватного образа настройте на **сервере Coolify** registry credentials с `read:packages`; не передавайте этот токен приложению. Для публикации отдельный PAT не нужен.

Сохраните исправный SHA-тег и digest образа. SHA-тег — соглашение о версии, а digest — идентификатор конкретного содержимого; не перезаписывайте опубликованные SHA-теги вручную.

## 2. Создать ресурс Coolify

Создайте Git-based **Docker Compose Application** для репозитория и ветки main, путь Compose — `compose.production.yml`. Используйте обычный режим обработки Compose: он создаёт сети и proxy labels для выбранного сервиса. **Raw (deploy file as-is)** не подходит без собственной настройки прокси/сетей. Несмотря на Git-источник, VPS ничего не собирает: в файле нет `build:`, только готовые `image:`.

Отключите Git auto-deploy и включите manual deployments only. Не добавляйте второй repository webhook: автоматический deploy позже будет вызывать Actions. Если UI текущей версии Coolify отличается, проверьте итоговый Compose: готовый образ, одна реплика, прежние volumes, отсутствие host-портов и публикации Qdrant.

Добавьте runtime Environment Variables:

| Переменная | Значение |
|---|---|
| `APP_IMAGE` | `ghcr.io/<owner>/<repository>` в нижнем регистре, без тега |
| `TAG` | Для первого запуска `sha-<проверенный полный SHA>`; для автодеплоя `latest` |
| `APP_BASE_URL` | Публичный origin, например `https://assistant.example.com`, **без :8000** |
| `ADMIN_USERNAME` | По умолчанию `manager` |
| `ADMIN_PASSWORD_HASH` | Хеш из `init-env`, не исходный пароль |
| `API_KEY` | Отдельный случайный ключ приложения из `init-env` |
| `PROXYAPI_KEY` | Ключ провайдера для индексации и ответов |
| `OBSERVABILITY_PROJECT` | По умолчанию `cleaning-kb`; уникальное стабильное имя при нескольких установках |

Лимиты/модели наследуют значения [README](../README.md#конфигурация). `APP_ENVIRONMENT=production`, путь SQLite и внутренний Qdrant уже заданы в Compose. Локальные `HOST_PORT`, `DATABASE_PATH`, `QDRANT_URL` и локальный `APP_VERSION` из init-env переносить не нужно.

Чтобы получить хеш и ключ без паролей в аргументах, локально выполните команды `init-env` из README. Для отдельного production-набора укажите `init-env --env-file .tmp/production.env` (каталог `.tmp` создайте заранее). Файл не коммитьте; перенесите нужные значения через защищённый UI Coolify. У хеша вида `pbkdf2_sha256$...` сохраните все `$`: при копировании значения из файла удалите только окружающие одинарные кавычки. Для текстового dotenv-импорта сохраните одинарные кавычки. Не делайте повторное shell-раскрытие значения и проверьте успешный вход после запуска.

## 3. Домен и HTTPS

Настройте DNS A на VPS; AAAA добавляйте только при рабочем IPv6. В Domains Coolify выберите сервис `api`, укажите `https://assistant.example.com:8000`. Суффикс 8000 задаёт **внутренний** порт прокси; посетитель открывает `https://assistant.example.com`.

Прокси должен быть доступен на стандартных HTTP/HTTPS-портах для выпуска сертификата и обслуживания запросов. Дополнительные внешние 8000, 6333, 6334 не нужны. Не назначайте Qdrant домен. TLS завершается на прокси, внутри сети допускается HTTP; Secure-cookie и CSRF привязаны к публичному `APP_BASE_URL`. Панель Coolify и мониторинга защищайте отдельно.

Выполните первый deploy вручную. Приложение должно стать healthy; health проверяет SQLite и Qdrant, без платного запроса. Запрос `GET https://assistant.example.com/health` должен вернуть `status=ok`, нужный SHA и обе успешные проверки. Наличие ключа/баланса модели health не подтверждает.

Откройте панель, войдите, убедитесь в корректности HTTPS-cookie. Загрузите корпус через Terminal сервиса api:

```sh
APP_BASE_URL=http://127.0.0.1:8000 APP_ENVIRONMENT=local python -m cleaning_kb seed
```

Переопределения применяются только к процессу seed: он обращается к HTTP API внутри контейнера. Сервер продолжает работать в production с HTTPS origin. Первая индексация платная; повтор готовых документов идемпотентен. Альтернатива — загрузить собственные документы через панель. Не загружайте негативные quality-фикстуры в рабочую базу.

## 4. Включить автоматический deploy

Создайте GitHub Environment `production`. Обязательное ручное одобрение environment по умолчанию не требуется; включайте по своей политике. В environment добавьте Secrets:

| Secret | Назначение |
|---|---|
| `COOLIFY_DEPLOY_WEBHOOK` | Скопированный Deploy Webhook (auth required) **одного** ресурса: HTTPS `/api/v1/deploy?uuid=...&force=false` |
| `COOLIFY_TOKEN` | Токен Coolify только с правом Deploy |

В Repository Variables добавьте `APP_PUBLIC_URL=https://assistant.example.com`. Установите `TAG=latest` в Coolify и сохраните. После первого успешного ручного запуска и проверки томов включите Repository Variable `PRODUCTION_DEPLOY_ENABLED=true`.

Следующий актуальный push main после CI публикует образ, затем выполняет один **POST** webhook. GET в актуальном API не запускает deploy. Скрипт принимает только один uuid, без tag-группы, и не следует редиректам с токеном. Ответ о принятии должен содержать один deployment выбранного ресурса. Затем до десяти минут проверяется публичный `/health`: старый healthy SHA не считается успехом. Сетевой timeout одной проверки — 15 секунд, шаг polling — до 10 секунд. Webhook автоматически не повторяется: неизвестный исход сначала разбирают в Coolify.

Запуски main сериализованы целиком и не отменяют начатый deploy; устаревший относительно head main запуск не публикует latest. После нескольких быстрых push проверьте итоговый SHA. Ручные деплои Coolify не входят в эту блокировку: не запускайте их одновременно с workflow. Git auto-deploy должен оставаться выключенным.

Параметры deploy передаются через окружение, URL/токен/тела ошибок не печатаются. Реальный бейдж CI/CD добавляйте в README после публикации под своим адресом репозитория.

## Данные, backup и восстановление

SQLite содержит документы, исходные фрагменты, кеш эмбеддингов, диалоги, аудит, отпечатки серверных сессий и учёт вызовов. Backup — чувствительные данные. Защищайте доступ, шифруйте при хранении вне VPS и задайте срок хранения/удаления по своей политике. Копия в том же app-data не защищает от потери сервера: выгружайте её в независимое хранилище. Восстановление старого снимка откатывает также ledger лимитов; проверьте фактические расходы провайдера и временно ограничьте доступ.

Перед обновлением в Terminal `api`:

```sh
python -m cleaning_kb backup --output /data/backups/before-update.sqlite3
```

Выбирайте каждый раз новое имя: существующий файл не перезаписывается. Команда использует SQLite backup API, включает подтверждённые записи WAL и выполняет integrity_check. Не копируйте один рабочий `.sqlite3` обычным `cp`, пока приложение пишет в WAL. Выгрузите файл из контейнера штатным способом сервера/Coolify. Например, на Docker-хосте после определения **своего** контейнера:

```sh
docker cp "$API_CONTAINER:/data/backups/before-update.sqlite3" ./before-update.sqlite3
```

Образ не меняет схему тайком: миграции имеют checksum. Если новая версия добавляет миграцию, откат старого приложения может отказаться открывать новую БД. До обновления сохраните SHA/digest, backup и фактические имена volumes.

При восстановлении остановите ресурс и отключите автодеплой/внешние записи. На хосте проверьте имя app-data через inspect именно своего контейнера. Запустите временный контейнер из образа приложения с этим томом и каталогом backup; сервис api в этот момент должен быть остановлен. Внутри контейнера:

1. Сохраните текущую БД и её `-wal`/`-shm` отдельно для разбора; не смешивайте их с backup.
2. Переместите старые файлы из рабочего пути. Скопируйте согласованный backup в `/data/cleaning-kb.sqlite3`, задайте владельца `10001:10001` и ограниченные права; старые WAL/SHM не должны остаться рядом с восстановленным файлом.
3. Запустите совместимый образ и проверьте integrity/migrations/историю. Старый backup может содержать действующие сессии: при инциденте смените ключи и отдельно отзовите восстановленные сессии.

Qdrant — производный индекс. Для быстрого возврата можно хранить его согласованные snapshots средствами Qdrant; для минимального сценария достаточно SQLite и восстановления индекса из сохранённого кеша. После потери Qdrant нажмите «Повторить индексацию» для каждого активного документа в панели. Простого seed недостаточно: ready-документы он не переиндексирует. При прежней модели/размерности это использует кеш без нового платного embedding. Смена модели/размерности требует отдельного плана reindex и бюджета. Копирование каталога работающего Qdrant обычным архивом не является согласованным backup.

## Откат приложения

1. Отключите `PRODUCTION_DEPLOY_ENABLED`, дождитесь завершения текущего workflow; остановите ручные параллельные деплои.
2. Установите `TAG=sha-<предыдущий исправный SHA>` и выполните ручной redeploy. Для точного закрепления используйте сохранённый digest при адаптации image-ссылки; latest для отката не подходит.
3. Если схема несовместима, сначала восстановите предрелизный backup по процедуре выше; новые данные после снимка будут потеряны. Автоматический downgrade миграций не реализован.
4. Проверьте SHA в health, вход, документы, диалог, отметки, сохранность volumes и журналы. Индекс при необходимости восстановите из кеша.
5. Исправьте исходники через обычный CI; верните `TAG=latest` перед включением автодеплоя. Зафиксируйте причину инцидента.

## Мониторинг и проверка установки

Подключите [Alloy и dashboard Grafana](../observability/README.md) к существующим Loki/Alloy/Grafana. В конфигурациях нет адресов личной инфраструктуры. Приложение пишет JSON stdout и не зависит от доступности Loki.

Перед признанием production готовым проверьте: один push → один deploy; новая версия healthy с верным SHA; публичны только согласованные домены; данные переживают redeploy; backup действительно восстанавливается; контрольный request_id находится в Grafana; секретов/текстов нет в доставленных логах. Локальная проверка файлов не заменяет этот прогон на вашем GitHub и VPS.

Официальная основа: [Coolify + Actions](https://coolify.io/docs/applications/sources/github/actions), [Compose](https://coolify.io/docs/applications/builds/docker-compose), [webhook POST](https://coolify.io/docs/core/automation/deploy-webhooks).
